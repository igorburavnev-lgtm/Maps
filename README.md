## Почему SortedMap на упорядоченных ключах так медленно

Если вставлять ключи по порядку — 1, 2, 3, 4, 5, ... — дерево поиска
вырождается в связный список: каждый новый ключ больше всех предыдущих,
поэтому узел всегда цепляется вправо от последнего. Структура получается
такая:

    1
     \
      2
       \
        3
         \
          4
           \
            5

Это уже не дерево, а цепочка глубины n. Поиск в ней — O(n), а не
O(log n), и вставка n ключей становится O(n²). Для 100 000 ключей это
~5·10⁹ операций сравнения — отсюда 20 секунд на замере.

В перемешанном порядке ключи ложатся более-менее равномерно, глубина
выходит близкой к log₂ n ≈ 17, и всё работает за миллисекунды.

**Вывод.** Заявленный у двоичного дерева поиска O(log n) верен только
для сбалансированного дерева. Настоящие `SortedDictionary` в .NET и
`TreeMap` в Java внутри самобалансирующиеся (красно-чёрное дерево),
и балансировка нужна ровно затем, чтобы этой вырожденной цепочки
не случалось ни при каком порядке вставки.
